# Comparison: the same API four ways

The same pet API, built with Gin + swaggo, oapi-codegen, Huma, and tack, then measured: how much is written by hand, what each produces, how each behaves on the same requests, and what happens when one field is renamed. Every number here comes from the files and logs in this directory. Nothing is estimated.

Measured on 2026-10-11 with Go 1.27.2 (windows/amd64), Node 22.15.0, TypeScript 5.9.3, and openapi-typescript 7.13.0.

| Variant | Directory | Versions |
| --- | --- | --- |
| Gin + swaggo | `gin-swaggo/` | gin v1.12.0, swag v1.16.6, gin-swagger v1.6.1 |
| oapi-codegen (spec-first) | `oapi-codegen/` | oapi-codegen v2.8.0, nethttp-middleware v1.2.0 (kin-openapi v0.142.0) |
| Huma | `huma/` | huma v2.39.1 |
| tack | `tack/` | tack v0.2.0 |

## What was built

Four routes with the same rules in every variant:

| Route | Rules |
| --- | --- |
| `GET /pets` | `kind` query, one of cat/dog/bird; `limit` query, 1-100, default 20 |
| `GET /pets/{id}` | `id` path, integer ≥ 1; 404 when missing |
| `POST /pets` | JSON body: `name` required, ≤ 50 chars; `kind` one of cat/dog/bird; 201 |
| `PUT /pets/{id}` | same body as POST; 404 when missing |

Each variant also has a TypeScript consumer, `ts/consumer.ts`, that reads `pet.name`, compiled with `tsc --strict`. The types it imports come from wherever that variant gets them: hand-written for Gin, generated by openapi-typescript for the other three.

Reproduce with `bash probe.sh` (builds each server, sends the same ten requests, exports the specs, generates the TypeScript, runs `tsc`). The rename logs are in `results/rename/`.

## 1. How much you write

| | Hand-written | Files | Generated by tools | Steps after each change |
| --- | --- | --- | --- | --- |
| Gin + swaggo | 224 lines (26 are `@` annotations) | `main.go`, `ts/api.ts` | `docs/docs.go` 237 lines | `swag init`, then edit `ts/api.ts` by hand |
| oapi-codegen | 244 lines | `openapi.yaml`, `cfg.yaml`, `main.go` | `api/api.gen.go` 477 lines, `ts/api.d.ts` 189 lines | `oapi-codegen`, `openapi-typescript` |
| Huma | 115 lines | `main.go` | `ts/api.d.ts` 262 lines | export `/openapi.json`, `openapi-typescript` |
| tack v0.2 | 105 lines | `main.go` | `ts/api.d.ts` 324 lines | export `/openapi.json`, `openapi-typescript` |

The consumer and `tsconfig.json` are the same size in every variant and are not counted.

Huma and tack are within ten lines of each other. tack's generated `api.d.ts` is larger because every operation lists its 400/413/415/422/500 problem responses.

## 2. Same requests, each server

Status codes from `probe.sh`:

| Request | Gin + swaggo | oapi-codegen | Huma | tack |
| --- | --- | --- | --- | --- |
| `POST /pets` valid | 201 | 201 | 201 | 201 |
| `POST /pets` empty name, kind "fish" | 400 | 400 | 422 | 422 |
| `POST /pets` missing kind | 400 | 400 | 422 | 422 |
| `POST /pets` malformed JSON | 400 | 400 | 400 | 400 |
| `GET /pets/1` | 200 | 200 | 200 | 200 |
| `GET /pets/999` | 404 | 404 | 404 | 404 |
| `GET /pets/abc` | 400 | 400 | 422 | 400 |
| `GET /pets?kind=cat` | 200 | 200 | 200 | 200 |
| `GET /pets?limit=500` | 400 | 400 | 422 | 422 |
| `PUT /pets/1` | 200 | 200 | 200 | 200 |
| Docs page | `/docs/index.html` 200 | none bundled | `/docs` 200 | `/docs` 200 |

What the client gets back for the empty name + bad kind body (`results/*/create-invalid.json`):

| | Format | Errors reported | Location of each error |
| --- | --- | --- | --- |
| Gin + swaggo | JSON, hand-written `Problem` shape | both, as one string: `Key: 'PetInput.Name' Error:Field validation for 'Name' failed on the 'required' tag ...` | Go field names, not JSON names |
| oapi-codegen | **`text/plain`**, although the spec declares a JSON `Problem` | only the first: `Error at "/kind": value is not one of the allowed values` | JSON pointer |
| Huma | JSON (RFC 9457 shape plus `$schema`) | both, with `location`, `message`, `value` | `body.kind`, `body.name` |
| tack | JSON (RFC 9457) | both, with `location`, `message` | `body.name`, `body.kind` |

Two things stand out. Gin leaks Go identifiers into client-facing messages unless you write a translation layer. oapi-codegen's validator middleware answers in plain text with the first error only, so the spec-first variant is the one whose server disagrees with its own spec out of the box.

## 3. Rename one field

The experiment: rename `name` to `petName` at the source of truth, fix only what the compiler forces, then check what the docs, the TypeScript types, and the consumer say. Logs: `results/rename/<variant>.txt`.

| | Source of truth | Forced by `go build` | Docs after the build passes | TypeScript after the build passes | Does `tsc` catch `pet.name` in the consumer? |
| --- | --- | --- | --- | --- | --- |
| Gin + swaggo | Go struct | 2 lines in `main.go` | **Stale** (`swagger.json` still says `name`) until you run `swag init` | **Stale**, forever, until someone edits `ts/api.ts` by hand | **No.** `tsc` passed against the stale hand-written types; the frontend would read `undefined` at runtime |
| oapi-codegen | `openapi.yaml` (4 edits: property and `required` in two schemas) | **Nothing**: the build passed with the old generated server, so the server now contradicts the spec. After `oapi-codegen`, 2 lines in `main.go` | Correct, because the YAML is the spec | **Stale** until you run `openapi-typescript` | Yes, after regenerating: `TS2339: Property 'name' does not exist` |
| Huma | Go struct | 2 lines in `main.go` | **Correct immediately**, no command (`/openapi.json` says `petName`) | **Stale** until you export the spec and run `openapi-typescript` | Yes, after regenerating |
| tack v0.2 | Go struct | 2 lines in `main.go` | **Correct immediately**, no command | **Stale** until you export the spec and run `openapi-typescript` | Yes, after regenerating |

Counting everything needed to end with correct code, docs, types, and consumer:

| | Files edited by hand | Commands run | Caught by a compiler | Could reach production silently |
| --- | --- | --- | --- | --- |
| Gin + swaggo | 3 (`main.go`, `ts/api.ts`, `consumer.ts`) | 1 (`swag init`) | Go usages only | docs, types, and the consumer |
| oapi-codegen | 3 (`openapi.yaml`, `main.go`, `consumer.ts`) | 2 | Go usages, consumer | a server built before `oapi-codegen` was rerun; types before `openapi-typescript` was rerun |
| Huma | 2 (`main.go`, `consumer.ts`) | 1 + spec export | Go usages, consumer | types before `openapi-typescript` was rerun |
| tack v0.2 | 2 (`main.go`, `consumer.ts`) | 1 + spec export | Go usages, consumer | types before `openapi-typescript` was rerun |

## 4. What this says about tack

On every measured axis, **tack v0.2 and Huma are the same**: same amount of code, docs that follow the struct with no extra command, and a TypeScript pipeline you assemble yourself and must remember to rerun. The only measured differences are cosmetic: tack's error body is plain RFC 9457 without a `$schema` field, and tack answers 400 rather than 422 for a non-integer path value.

The gap that remains in every variant is the last column: the TypeScript types go stale silently between the Go change and the next time someone runs the generator. Nothing measured here closes it. The parts of the plan meant to close it are not built yet:

- `tack check` (v0.4): CI fails when the committed client is older than the code.
- `tack dev` (v0.5): the client regenerates on save, so the stale window is seconds and the consumer fails inside the editor.
- Typed error unions (v0.4) and Zod schemas from `validate` tags (v0.5): nothing in this comparison measures them, because no variant here has them.

So the honest reading is: as of v0.2, tack has no measured advantage over Huma, and Huma has years of production use, more adapters, and a community. The case for continuing rests entirely on v0.3 through v0.5. If those ship as planned, this experiment should be rerun with a fifth column, "tack v0.5", where the rename ends with one file edited, zero commands, and the consumer failing in the editor. If they do not ship, the better use of the same effort is contributing a client generator and a dev loop to Huma.
